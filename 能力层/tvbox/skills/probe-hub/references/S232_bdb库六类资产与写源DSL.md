## ★ 零、先纠一处对象错位（这一条比后面全部内容都重要）

上一轮（11-15 上午）判「这个包不含自动写源工具」，依据是**关键词扫描零命中**：
按「写源／一键生成／自动生成／生成源／打包」五个词全包搜，结果 0 条。

**这个判定错了。** 包里确实有写源产物，只是它不使用「写源」这两个字。
真正的特征是 `[工具:…]` 指令语法，按它重扫命中 **8 个文件**：

| 文件 | `[工具:]` 处数 |
|---|---|
| `xbpq/91探花.json` | 6 |
| `xbpq/91吃瓜备用1.json` | 4 |
| `xbpq/聚合一.json` / `聚合.json` / `绿色仓库.json` / `一起玩.json` / `91吃瓜.json` / `404.json` | 各 1 |

> **这是一次「判据关键词 ≠ 对象特征」的现场复现**（病15 第 12 例，已入台账）：
> 「这个包里有没有 X」这个判断，用 X 的**名字**去扫，而对象里 X 是以**语法形态**存在的。
> 真正的教训不是「这次漏了」，而是：**声称「某物不存在」之前，必须先说明用什么特征判的、
> 这个特征在正样本上验证过没有**。上一轮那句话的正确写法是「按关键词扫描零命中，
> 但未验证关键词是否为该对象的有效特征」——那是「无法判定」，不是「没有」。

## 二、★ 核心：`xbpq/` 是写源 DSL，属于**第二种写源范式**

S231 吸收的是「写源引擎的实现」——`OK影视一键写py.py` 2587 行 Python，**代码生成路线**：
工具读网站 → 吐出一个 `.py` 源文件。

`xbpq/*.json` 给的是**另一条路线**：**配置驱动**。工具不生成代码，而是解释执行一份
JSON 模板；同一个引擎可以跑任意站点模板，站点差异全部落在 JSON 里。

### 2.1 语法四件套（从 8 个模板文件里实际抽出的清单，非推测）

**① 变量引用 `{{名}}`**——跨字段复用，先算后用：

```
"发布页": "https://…/"            →  后面所有字段用 {{发布页}} 引用
"key截取": "{{发布页}}[工具:源码#key:*\"截取\"]"
"key":     "{{key截取}}[工具:SHA]"
"iv":      "{{key}}[工具:1截取16]"
"域名-c":  "https://{{作者}}.{{后缀}}/"
```
出现频次：`{{域名-c}}` 56 次最高，其次各站 URL 变量（`{{主页url}}` 6 次等），共 20+ 个变量名。

**② 工具指令 `[工具:步骤#步骤#…]`**——`#` 串联的管道：

| 指令 | 次数 | 作用 |
|---|---|---|
| `源码` | 8 | 取目标页源码（管道起点，最常用） |
| `源码转b64` / `解b64` | 2 / 2 | base64 编解码 |
| `解密aes` / `解aes` | 2 / 1 | AES 解密，参数串成 `-key-iv-AES/CBC/PKCS7Padding` |
| `解url` | 2 | URL 解码 |
| `重定向` | 1 | 跟跳转取最终地址 |
| `words.random` / `随机字符` | 2 / 1 | 生成随机串，带 `-3-唯一` 参数（长度-唯一性） |
| `SHA` | 1 | 摘要 |
| `1截取16` | 1 | 取前 N 字符 |
| `document.write` | 2 | 抽 JS 写入内容 |
| `*"截取"` | — | 定位锚点后截取，通用步骤 |

一个五步管道的真实样本：

```
"后缀": "{{发布页}}[工具:源码#data:*\"截取\"#解aes-{{key}}-{{iv}}-AES/CBC/PKCS7Padding#\"zz_line\":*\"截取\"]"
```
读法：取发布页源码 → 定位 `data:` 并截取 → 用 {{key}}/{{iv}} AES-CBC 解密 → 定位 `"zz_line":` 再截取。

**③ 选择器算子**（这是它比 S231 的固定正则强的地方）：

| 算子 | 次数 | 语义 |
|---|---|---|
| `&&` | 262 | 取两段之间的内容（左界`&&`右界） |
| `\|\|` | 252 | **多套选择器备选**——一套失效自动试下一套 |
| `--` | 222 | 分组/标注分隔 |
| `📌` | 37 | 分组锚点名（如 `📌探花标签--<div class="tags-group">&&`） |
| `分割(前:<a hr)` | 4 | 先按锚点分割再取 |

`||` 252 次意味着**模板作者自己就在做多形态兜底**——这跟我们 `play_sets` 六层兜底、
`resolve_play_page` 七层的思路同源，只是他们把它做成了声明式。

**④ 运行时变量**：`{catePg}`（分类页，63 次）、`{wd}`（搜索词，14）、`{pg}`（页码，14）
——与 `{{}}`（编译期求值）区分开，`{}` 是运行期替换。

### 2.2 两条范式的取舍（探源司该怎么用）

| | S231 代码生成 | S232 配置驱动 |
|---|---|---|
| 产物 | 一个 `.py` 文件 | 一份 JSON 模板 |
| 能力上限 | 无上限（任意 Python） | 受 DSL 指令集限制 |
| 加密站 | 手写 RSA/AES 代码 | `[工具:解密aes-…]` 一行 |
| 换站成本 | 重写代码 | 改 JSON 字段 |
| 可读性 | 要读代码 | 字段名即语义（"标题"/"播放链接"） |
| 失败诊断 | 报错行号明确 | 管道哪一步断了不可见 |

> **结论**：DSL 适合**形态固定的批量站**（同一套 CMS 模板的几百个站，改域名即可）；
> 代码生成适合**形态异常的站**（加密接口、签名、私有协议）。
> 两者不是替代关系——**探源司现在的 recon 恰好是「先判定形态、再决定路线」的那一步**，
> 等于已经站在两条路的分岔口上，缺的是「DSL 路线」这个下游出口。

> ⚠ **与本仓既有边界的交叉（先看这条再动手）**：`SKILL.md` §3.12 四条铁律③ 明确写着
> 「**不做「配置驱动自动生成源」**」（依据：遮天法 v3.1 十项能力七项无调用点，诚实边界不是缺口）。
> 所以 S232 的吸收方向是「**认得出 DSL 形态、判得清该走哪条路线**」——是**侦察**，不是**施工**。
> 若有人读完本节就想在探源司里实现一个 DSL 解释器，那是与铁律③正面冲突，须先改铁律再谈实现。
> 本节的价值在 §五 待办第 2 条（recon 增「路线判定」出口），不在「多写一个引擎」。

## 三、`lib/pan/` 网盘链：现有能力缺的那一段

三个网盘实现，都是完整「分享链接 → 转存 → 取直链」链路：

| 文件 | 入口 | 关键路径 |
|---|---|---|
| `pan/quark.js` | `drive.quark.cn/1/clouddrive/` | `file/sort` 列目录；cookie 含 `__puus=` 时定期刷新 |
| `pan/uc.js` | `pc-api.uc.cn/1/clouddrive` | `getShareToken` → `getFilesByShareUrl` → `save` → `refreshCookie`；另接外部 token 服务 `api.extscreen.com/ucdrive/token` |
| `pan/baidu.js` | `/share/streaming` | `getRandsk` → `getShareList` → `getSharepath` → `getSign` → `getWebPlayUrls` |
| `pans.js` | 调度层 | 只导出 `Quark/Baidu/UC` 三家（另 5 家 Ali/Cloud/123/yun/baidu2 已注释掉） |

**对探源司的意义**：`resolve_play_page` 现在遇到网盘链接只能 `NETDISK` 前置识别 + `parse=0`
直塞给壳，**不会解析出可播地址**。这套代码给了完整的 API 路径与参数顺序。

**吸收边界（写死，避免越线）**：只吸收**协议形态**（路径、参数、状态机），不内置任何
cookie/token，不做绕过登录的实现。转存属于用户对自己账号的操作，工具侧只提供
「按用户自己给的凭证调用」这一层。`api.extscreen.com/ucdrive/token` 这类第三方 token
服务**不接入**——依赖外部服务等于把可用性押在别人身上。

## 四、`py/` 与 `open/`：样本价值大于代码价值

- `py/` 46 个 `.py` **全部实现 `playerContent`**，形态分布本身就是「第 7 条金律」的样本来源
  （已用于 S231 实测，见该文档 §五）。另有 1 个 `瓜子.py.bak` 未计。
- 单个文件最大的两个是 `资源管理.py`（351 KB）与 `资源管理备用.py`（284 KB）：前者是
  **功能大杂烩**（`XLSXMagnetParser` / `MagnetLinkParser` / `ComicReader` / `RadioProgramFetcher` /
  `DatabaseReader` / `NovelParser` / `CoverScanRecord` / `WebActionBrowser` / `GameHall` 十余个类
  塞一个文件），不是写源工具，**不建议深挖**——它是一个 App 的全部业务，与写源无关。
- `open/wanpan.js` 是**网盘站聚合**，内含 8+ 站点的多域名列表（`DOM_CFG`），每站 5 个域名
  并发检测。这个结构与本仓 `monitor_domains.json` 同形，**可直接作为域名监控的真实数据源**。
- `js/` 21 个与 `config/` 2 个：只做形态参考，不深挖（js 侧能力本仓已由 shellcrack/forge 覆盖）。
