# 软规则硬化矩阵（core-8 十八条 × 钩子可观测性）

> 目的：回答「哪些软条款能用钩子变硬、哪些永远硬不起来」。
> 判据不是「重要不重要」，而是**钩子能不能观测到它在发生**。
> 版本：2026-11-14 首版。改条款或改钩子能力后必须回来更新本表。

## 一、钩子只有四个观测面

平台支持 9 个事件（`PreToolUse` / `PostToolUse` / `UserPromptSubmit` / `Stop` /
`SubagentStop` / `SessionStart` / `SessionEnd` / `PreCompact` / `Notification`），
但对「行为是否正确」真正有用的观测面只有四个：

| 观测面 | 事件 | 能看到什么 | 看不到什么 |
|---|---|---|---|
| ① 命令串 | PreToolUse·Bash | `tool_input.command` 原文 | 命令跑起来之后会发生什么 |
| ② 文件路径 | PreToolUse·Write/Edit | `tool_input.file_path` | 写进去的内容对不对 |
| ③ 工具结果 | PostToolUse | `tool_response` | 模型怎么理解这个结果 |
| ④ 回合文本 | Stop | transcript 路径 + 本轮全部消息 | 模型的内部推理过程 |

**一个条款能被硬化，前提是它的违反行为会在这四个面之一留下可正则化的痕迹。**
做不到这一点的条款，加钩子只会造出「看着拦、其实没拦」的假闸——比不设防更糟。

## 二、六级强度（本表用这套刻度）

| 级别 | 含义 | 违反后果 |
|---|---|---|
| **S1 硬阻断** | PreToolUse deny，动作根本发不出去 | 做不成 |
| **S2 拽回** | Stop 钩子 exit 2，模型被拉回来继续（`stopHookFeedback` 注入） | 说不完，得重说 |
| **S3 事后提醒** | PostToolUse `type: prompt`，动作已发生，事后提示模型自查 | 可能已被忽略 |
| **S4 开机注入** | SessionStart 注入上下文 | 模型可能不读 |
| **S5 变更闸** | pre-commit / verify.sh，改动能拦、运行时行为拦不住 | 事后拦 |
| **S6 纯文本** | 只写在规则文件里 | 全凭模型自觉 |

## 三、逐条矩阵

| 条 | 内容 | 可观测面 | 当前强度 | 可达到 | 判定依据 |
|---|---|---|---|---|---|
| B-01 | 语言 | ④ 回合文本 | S6 | S2（不推荐） | 中英混排误报极高，「JSON / token」等术语本就该保留英文 |
| B-02 | 三态诚实 | 无 | S6 | **硬化不了** | 「是不是真阳性」是语义判断，正则判不了真假 |
| B-03 | 先验开工 | ① 命令串 | S6 | S1（慎用） | 可拦「本会话首个 Bash 不是 pwd/git log」，但技能内也会先 Read，易误伤 |
| B-04 | 并行 | 无 | S6 | **硬化不了** | 钩子看不到「本条之后还有几条独立动作」，无从判断该不该并行 |
| B-05 | 零明文凭证 | ①② | S5（secret_scan） | **S1** | `git add .env`、写 `.env`/`credentials*` 路径可直接拦 |
| B-06 | 事实源 | 无 | S6 | 硬化不了 | 「某规则是否已退役」要靠查文件，不是行为模式 |
| B-07 | 换模型对账 | SessionStart | S6 | **S4** | 开机即注入 `handoff_latest.md`，比「靠模型记得读」硬一级 |
| B-08 | 正本入口 | ① 命令串 | S6 | S3 | 可探测「同类命令第二次执行」提示查入口，但无法判断第一次是否查过 |
| B-09 | 产物纪律 | ② 文件路径 | S6 | **S1** | 写会话产物区/交付目录路径可直接拦 |
| B-10 | 拦截即停止 | ③ 工具结果+① | S6 | S3 | 需跨调用比对「上条输出含拒收 + 本条同类重试」，状态机可行但误报不低 |
| B-11 | 后台与落盘 | ① 命令串 | S6 | S3 | 无法预判时长；只能拦已知长命令（`clone` 大仓 / `npm install`）且无误报太难 |
| B-12 | 回合收敛 | ④ 回合文本 | S6 | S2 | Stop 时可判「本轮有无落点段」，但「做了什么」写没写清仍是语义 |
| B-13 | 完成态凭落点 | ④ 回合文本 | S6 | **S2** | 本轮出现「完成/通过/已修复」且无 `commit sha` / `rc=` / `文件:行号` → 拽回 |
| B-14 | 账目三齐 | ⑤ 变更闸 | **S5**（commit-msg 四字段） | S5 | 已是最硬一档：登记与提交同源，改动能拦 |
| B-15 | 孤例还是模式 | 无 | S6 | 硬化不了 | 「是不是模式」要全仓扫描，钩子不跑这类分析 |
| B-16 | 双核必保 | ① 命令串 | **S1（已落地 G4）** | S1 | `rm/mv/git rm` 目标含 `tvbox-core` / `probe-hub` 直接拦 |
| B-17 | 代号即确认 | 无 | S6 | 硬化不了 | 需要理解用户短代号指向上一条回复的哪个选项 |
| B-18 | 产出可溯源 | ④ 回合文本 | S6 | S2 | 可判「交付段有无『N 条有出处 / M 条无出处』」 |

**统计：18 条里 12 条硬化不了或不该硬（B-01/02/04/06/08/10/11/12/15/17 等），
真正值得硬化的只有 6 条（B-05 / B-07 / B-09 / B-13 / B-14 / B-16 / B-18 中已做 2 条）。**
这个比例本身就是答案：**钩子不是万能的，它只能硬化「行为」，硬化不了「判断」。**

## 四、已落地（S1 / S5）

| 规则 | 条款 | 实现 | 实证 |
|---|---|---|---|
| G1 `--no-verify` | B-14 的旁路 | `hooks/guard_cmd.py` | 实测 `git commit --no-verify` 被平台阻断 |
| G2 `rm -rf /`、`rm -rf ~` | 灾难防护 | 同上 | 正则正反例 + 回归 |
| G3 强推 main | B-14 的旁路 | 同上 | 实测 `git push --force origin main` 被阻断 |
| G4 删/移双核 | **B-16** | 同上 | 实测 `rm -rf .../tvbox-core; echo ok` 被阻断（首版漏判 `;` 分隔符，已修） |
| 提交四字段 | B-14 | `hooks/commit-msg` | 缺字段直接拒提交 |

## 五、可落地但未做（按性价比排序）

1. **B-13 → S2（Stop 拽回）**：价值最高。它治的是本项目最高频的毛病——「说完成了但拿不出落点」。
   代价：Stop 钩子每次结束都跑，需 `stop_hook_active` 防死循环；文本匹配会有误报，
   必须只判「断言词 + 证据词」共现，不能判语义。
2. **B-05 → S1**：拦 `git add` 凭证文件名、拦 Write 到 `.env` / `credentials*`。
   代价低、误报低，但**前提是先确认平台真的执行 `permissions.deny` 之外的白名单语义**。
3. **B-07 → S4（SessionStart 注入）**：开机注入交接摘要首段。
   代价最低，但只是「提醒」级，不等于读了。
4. **B-09 → S1**：拦写产物区路径。需要先有一份「产物区路径清单」作为判据真源。

## 六、明确不做的

- **B-02 三态诚实加钩子**：正则判不了「这是不是真阳性」。硬加只会让模型学会换词绕过，
  真正的三态诚实只能靠产物审核与人工抽检。
- **B-01 语言加 Stop 判**：中文里夹 `token`、`JSON`、`commit sha` 是常态，误报率会高到
  让人关掉钩子——钩子被关掉等于全域失防，代价远大于收益。

## 七、维护

- 新增钩子规则后必须回填本表「当前强度」列，否则本表变成过时文档（病13 家族）。
- 判据三件套照旧：造违例 / 具体规则拦下 / 元变异（清空规则后违例必须溜过）。
- 本表与 `docs/工程纪律.md` §10（验证到末端）、`verify/tests/test_guard_cmd.py` 三处同源，
  改一处必须改另两处。
